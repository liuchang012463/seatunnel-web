# 数据中台引接分系统 · UI/UX 审计报告

> 分支：`redesign`（2026-09-12）。本文档只做审计与问题定义，不修改任何正式 UI。
> 审计人：ZCode（frontend-design 工作流 AUDIT 阶段产出）。

## 1. 审计范围与方法

- **方式**：Playwright + Chromium 驱动真实运行的系统（前端 `127.0.0.1:8000`，Umi Max 4 dev；后端 `:9527` 真实测试库数据），视口 `1440×1000`，逐页截图 + 可访问性快照 + 控制台错误采集；结合源码（`design-system.less`、`app.tsx`、`src/menuData.tsx`、`routes.ts`、各页面组件）交叉验证。
- **覆盖页面**：数据源管理（卡片/列表/新建弹层/主数据）、数据探查（概览/任务/结果/内嵌详情工作台）、数据引接（任务概览、离线/实时/文件引接、任务详情）、入湖管理（物理/数据湖/生命周期）、运行运维（引接引擎、探查引擎、告警）、数据采报、引接态势（占位）、浅色模式、控制台错误。
- **截图证据**：`tmp/ui-audit/audit-01..22-*.png`（audit 分支工作区，不入库正式目录）。

## 2. 业务与信息架构理解

产品定位：**数据中台的引接分系统**——把异构数据源（关系型/OLAP/消息队列/文件/API）引接入湖（Doris），并提供元数据探查、任务运维与告警。核心用户任务按频率排序：

1. **看状态**：引接任务/数据源/引擎今天是否正常，哪里失败（任务概览、告警、链路健康列）。
2. **管数据源**：登记、连通检测、探查、启停注销（数据源管理）。
3. **建链路**：配置离线/实时/文件引接任务（单表/多表/脚本四种向导）。
4. **查元数据**：浏览探查结果、看表结构/样本/画像（探查结果工作台）。
5. **管入湖资源**：ODS 建库、生命周期策略、逻辑访问。

信息架构（`src/menuData.tsx`，8 个一级组）：

```
引接态势 /bi（占位） · 数据源管理 /data-source
数据探查（概览/任务/结果） · 数据采报 /reporting
数据引接（任务概览/离线/实时/文件/云边/边缘/拓扑）
运行运维（引接引擎/探查引擎/数据湖/告警/协议/安全加密）
入湖管理（物理/逻辑/生命周期） · 系统管理（参数知识/开放接口）
```

IA 本身清晰，主要问题在**导航呈现**与**页面内部的信息设计**（见下）。

## 3. 全局发现（按严重度）

### G1 · 明暗两套设计语言并存，且切换后渲染断裂（严重）

- 暗色（默认，军工暗蓝 `#001922/#002E41/#2187A8/#4DD2FF`，圆角 2-4px）与浅色（`#4051B5` 靛蓝、圆角 16-24px 胶囊按钮）是**两套完全不同的人格**（`design-system.less` 848-1339 行）。
- 实测切换浅色后（audit-21）：筛选栏、卡片变浅色，但「数据源清单」面板仍是深色底配深色标题，文字近乎不可读——同屏出现两种主题的碎片。
- 根因：浅色不是令牌切换，而是**选择器级补丁**（`html[data-st-theme="light"]` 下再覆写上百条规则），页面里大量 Tailwind 任意值类（`bg-[#F8FAFC]` 等）只能靠逐个类名映射（549-676 行 "Tailwind neutral compatibility layer"）和内联样式属性匹配（`[style*="background: white"]`，966-992 行）兜底。
- **影响**：任何新页面/新组件都可能掉进两套主题的夹缝；视觉一致性无法靠制度保证。

### G2 · 样式实现架构不可持续（严重，工程性）

- `design-system.less` 1890 行，全文件大量 `!important` 覆盖 antd；`theme.ts`/`app.tsx` 未使用 antd 5 `ConfigProvider theme={{algorithm: theme.darkAlgorithm, token}}` 的正规定制路径（Context7 已核对官方做法），而是"静态 CSS 变量 + 运行时再 `!important` 改写 `--ant-*`"。
- 后果：组件升级即碎、优先级战争、无法按组件粒度定制；这是多数视觉不一致问题的共同根因。

### G3 · 主导航不可读：纯图标侧栏 + 激活态错位（严重，可用性）

- 8 个一级组、20+ 页面全部收进 48px 纯图标栏，无文字、无分组标识（audit-01）。图标语义模糊（引接态势 vs 任务概览 vs 探查概览都是图表类图标）。
- **实测 bug**：父级菜单激活时，选中背景渲染成一个与图标列脱节的悬空亮色方块（audit-03、audit-10 左侧可见），看起来像渲染错误。
- 顶部栏近乎空置：无页面标题、无面包屑、无环境标识、无用户区，只放了主题切换——全局层没有承载任何信息。

### G4 · 表格语言五处不统一（主要）

同一数据网格在不同页面呈现为：

1. 表头：饱和青色实心带 `#2187A8` 白字（数据源列表/引接任务）；
2. 表头：同色但行内斑马纹 + **hover 行变棕色 `#824c22`**（`design-system.less` 396-398 行，暗色下的明显异物）；
3. 全单元格网格线（边框-complete）→"坐标纸"观感；
4. 探查任务页：低饱和表头 + 行分隔线（较接近合理）；
5. 列表视图列头中英混用（`Resource Status` vs 中文列）。

行高 38px、内容 14px 尚可，但**关键列缺失**：数据源列表无类型图标列、无单位/业务系统、无更新时间；名称/URL 截断无 tooltip 层级。

### G5 · 操作层级失衡：动作链接过载（主要）

- 数据源卡片每张 5-6 个同权重文字动作（测试连接/探查结果/停用/注销/删除），10 张卡 = 50+ 个链接；**删除（危险）与测试连接平级并排**（audit-01/02）。
- 引接任务列表每行 3 个动作 + 底部批量栏 7-8 个按钮常驻（含"暂停并保存检查点"等低频项）（audit-08）；文件引接空列表也显示整排批量按钮。
- 没有主次：看不出哪个是"下一步最可能做的动作"。

### G6 · 标签（Tag）噪声（主要）

- 每张数据源卡 4-5 个胶囊标签：连通正常/已启用/未探查/分类/系统内置（audit-01）。类型本可用图标+列表达，分类标签与筛选 chips 重复；每卡固定 3 个绿色系标签，扫视时无法快速定位**异常项**。
- 状态色彩语义没有全局约定：失败在引接列表是红字纯文本，在探查页是 outline tag，在 /bi 是黄绿色 tag（audit-19），在 Client 页是英文 "Healthy"。

### G7 · 图表与强调色跑色（主要）

- 任务概览 `/metrics`：ECharts 使用默认紫蓝色柱状图（audit-06），KPI 卡图标紫/黄/紫——全部脱离青蓝令牌；`echarts` 未注册自定义主题（源码确认仅 echarts-for-react 默认注入）。
- Client 页进度条偏靛蓝、探查引擎页 DOWN/不兼容红色用于数值文本（audit-16）——语义色当装饰色用。

### G8 · 筛选/工具条模式混乱（主要）

- 引接三页的筛选区：`任务名：[输入] 创建时间：[起→止] 状态:[选择] [搜索][重置] 展开╏ 排序╏ [↓名称][↓配置时间]`——其中"展开/排序"是**竖排文字按钮**（audit-07/08/09），排序同时出现在按钮组和表格列头两处；label 冒号内联对不齐。
- 数据源页筛选则拆成两行（下拉行 + 分类 chips 行），分类 chips 与"按类型筛选"下拉在新建弹层里又出现第三种形态。

### G9 · 术语与语汇不一致（中等）

- 菜单「引接引擎管理」↔ 页面标题「Client 管理」；健康值 `Healthy` 英文；列头 `Resource Status`；连接器副标题暴露内部代码（`Jdbc`/`S3File`/`SttpFile`）(audit-22)；主数据页直接显示 `UNIT_102YJZ3/SYSTEM_2VD3NH` 内部标识而非名称（audit-11）。
- 任务行前缀「任务名：」「任务定义ID：」重复罗列 label（audit-07），信息用"全 label + 值"而非排版层级表达。

### G10 · 状态断裂与空态缺陷（中等）

- 离线任务详情页（无有效 id 时）整页只有一行「暂无数据」，无页头、无返回、无引导（audit-10）——深层路由的兜底态缺失。
- 健康状态「失败」无行内下钻入口（错误信息藏在「更多」里），监控动线断。
- 告警页 CTA 重复出现两处（工具条 + 空态）；水印 `admin` 全屏平铺过强（audit-18）。

### G11 · 控制台噪声（低，但量写真）

- 每页 26-47 条 console error：React Intl `menu.运行运维.引接引擎管理/数据湖管理` fallback 刷屏（ProLayout menuDataRender 用中文 name 直接当 intl key）、antd `findDOMNode`/`destroyOnClose`/静态 message 弃用警告。真实用户不可见，但掩盖真正的报错。

### G12 · 密度两极（低）

- 引接任务行高约 128px（内嵌 KV 列表对齐松散），而数据源列表视图每行只有 5 列稀疏排布；同屏信息量差距 4 倍以上。中台用户普遍需要"一屏更多行"，当前没有密度选项。

## 5. 现状中值得保留的资产

- **探查三栏工作台**（类型导航 / 结果列表 / Inspector）与 `EXPLORATION TYPES/METADATA RESULTS/INSPECTOR` 眉题体系——已是差异化的"工作台"语言，值得延续并收敛。
- **引接任务的 A→B 链路行**概念（源→目标含图标与库名）——正确的领域表达，需要排版收紧。
- **底部批量操作栏**（选中后启用）模式正确。
- **空态带下一步引导**的文案习惯（探查详情空态、DESIGN.md 已有规约）。
- `--st-*` 令牌命名与 DESIGN.md 的字号/控件高度规范——底子可用，需要升级而不是推翻。
- 军工暗蓝基调本身辨识度高，不在"generic AI dashboard"之列，应保留并提纯。

## 6. 审计结论

问题的**根因**集中在三层：① 双主题双语言没有统一的令牌与算法底座（G1/G2）；② 缺一套强制共享的"表格/状态/工具条/动作"组件语义（G4-G8）；③ 全局壳层（导航/页头）没有承担信息架构职责（G3/G10）。视觉方向（军工暗蓝）本身成立，不需要换方向，需要**提纯与制度化**。

对应的方向与系统方案见 [`DESIGN.md`](../DESIGN.md)。本报告中的原型页面和截图是历史审计证据；相关运行时原型与静态参考原型现已退役，不再作为正式 UI 或开发入口。
