> 文档性质：项目总体阶段计划 / 《软件开发计划》（SDP）编制输入<br>
> 版本：V0.2（策划草案，纳入 TDuck 技术路线）<br>
> 编制日期：2026-07-19<br>
> 适用范围：数据采集引接软件、数据资产管理软件<br>
> 依据：GJB 2786A-2009、GJB 438C-2021、合同技术要求及当前功能/性能拆解材料<br>

## 1. 策划结论

本项目建议采用“受控增量 + V 模型验证”的研制方式，将数据采集引接软件和数据资产管理软件分别作为两个计算机软件配置项（CSCI）管理，在统一的项目策划、配置管理、质量保证和测试体系下并行研制。

总体安排如下：

- 计划周期按 48 周建立首版基线，起点 W1 为项目正式启动日；外部评审等待、第三方测评排队和需方环境未就绪时间不计入净研制工期。
- 数据采集引接软件采用“双核心组件”复用路线：数据采报功能以 TDuck 受控版本为核心组件，在线引接、任务编排与执行以当前 SeaTunnel-Web 企业 Fork 和 Apache SeaTunnel 为核心组件；项目能力优先通过独立模块、SPI、适配器和事件接口实现。
- 数据资产管理软件以 OpenMetadata 为元数据能力底座，通过受控版本、适配层和统一门户集成满足合同；不能把 OpenMetadata 已有能力等同于合同指标已满足，所有指标仍须经需求分配、设计和测试证实。
- 合同最低指标是验收判据；指标 Markdown 中的“20% 以上优化”数值作为内部设计目标和性能裕量目标，不得替代合同基线，也不得在测试前作为已实现结论。
- GJB 2786A 的活动要求贯穿全过程；GJB 438C 的文档不是项目结束时补写，而是随需求、设计、实现、测试和配置基线同步形成。

### 2.2 需求基线前必须闭环的问题

1. **数据资产资源编目存在漏项。** 合同 `ZCGL-GN-03` 要求对领域数据、对象数据、主题数据进行资源编目、查询和浏览；当前 Sheet3 和指标 Markdown 主要把“数据资源编目”拆成标签管理，实际对应的是 `ZCGL-GN-04`，没有单独覆盖 `ZCGL-GN-03`。需求分析阶段必须补齐模块、软件需求和测试方法。
2. **合同总表存在疑似错标。** Sheet1 第 239～240 行再次使用 `ZCGL-XN-01`、`ZCGL-XN-02`，内容为“综合态势展示时间”和“系统日志管理”，且位于共享交换与安全审计指标之间，可能是配置项名称和标识复制错误。未经合同/总体单位书面确认，不纳入本软件验收基线，也不得直接删除。
3. **合同值与内部目标必须双轨管理。** 例如采集全量/增量合同值为 1000/500 条每秒，内部目标为 1500/700 条每秒；测试用例要同时记录“合同符合性结论”和“设计目标达成情况”。
4. **性能口径需提前固化。** “不包括大字段”“典型有线网络”“单行 200 字节”“本地查询”“低实时/高实时”等条件必须在 SRS、STP、STD 中给出可复现定义，包括硬件、操作系统、数据库、缓存冷热状态、数据分布、并发度和计时边界。
5. **需取得受控版 GJB 2786A-2009。** 当前材料中只有 GJB 438C-2021 Word/RTF 版。正式声称符合 GJB 2786A 前，配置管理员必须取得合法、受控、可追溯的标准副本，建立逐条符合性矩阵，并由质量保证人员复核。本计划以 GJB 438C 附录 A 明确列出的 GJB 2786 软件开发活动作为阶段骨架，但不替代对 GJB 2786A 正文逐条审核。

## 3. 软件配置项与技术边界

### 3.1 配置项划分

| 配置项 | 建议标识 | 主要组成 | 复用软件 |
| --- | --- | --- | --- |
| 数据采集引接软件 CSCI | `CJYJ-CSCI` | 采报门户与表单服务、采集引接服务、边缘端、协议/文件适配器、监控告警、报表、OpenMetadata 血缘/拓扑适配器 | TDuck、SeaTunnel-Web、Apache SeaTunnel 及连接器 |
| 数据资产管理软件 CSCI | `ZCGL-CSCI` | 统一资产门户、治理工作流、标准/主数据/字典/质量扩展、检索与态势、时空快视、评估分析、OpenMetadata 适配器 | OpenMetadata 及其受控依赖 |

两个 CSCI 共用统一身份、组织、权限、审计、消息、文件、搜索和可观测性能力时，应把这些能力定义为明确的公共服务/软件单元，规定接口、责任边界和故障隔离，不得由两个软件各自复制实现。

### 3.2 TDuck 复用边界

TDuck 作为数据采报功能的核心组件，优先复用其表单设计、发布、填写、数据收集、结果查询/导出以及经项目验证可用的 API、Webhook 和统计能力。项目应在 B0 阶段确定社区版或商业版产品形态、受控版本、源代码与构建可得性、许可证和离线部署条件，并形成能力差距与安全评估记录。

TDuck 官方公开材料显示社区版、Pro 和 TDuckX 的功能及授权形态不同，且社区版表单编辑器并非完整开源；因此“采用 TDuck”尚不足以确定可交付基线，`TBC-CJYJ-TDUCK-001` 必须在 SRR 前以书面版本/授权/源码结论关闭。复用分析输入包括 [TDuck 官方仓库](https://github.com/TDuckCloud/tduck-front) 和 [TDuck 官方功能文档](https://doc.tduckcloud.com/functionDesc/)。

下列原则构成复用约束：

- TDuck 的用户、组织和权限模型通过适配层接入项目统一身份与权限体系，不得形成绕过统一鉴权的独立账户域；
- 表单、字段、发布版本、采报任务、填报批次和采报结果使用项目稳定标识，并与 TDuck 内部标识建立可追踪映射；
- 组件已有功能不能直接视为合同要求已满足，语义错误识别纠正、任务分配、典型工作模式、合同格式报告、保密审计和性能指标仍须逐条开展差距分析与合格性验证；
- 集成优先采用公开 API、Webhook、插件或独立适配服务；确需修改 TDuck 核心代码时，按上游补丁登记、回归测试和升级合并策略管理；
- TDuck 不直接访问 SeaTunnel-Web 或 OpenMetadata 内部数据库，跨组件数据交换通过受控接口和事件完成。

### 3.3 SeaTunnel-Web 复用边界

当前仓库可作为下列能力的工程基础：

- 数据源连接、连通性验证和元数据读取；
- 批处理、流处理、CDC、脚本和可视化 DAG 任务定义；
- Source/Transform/Sink 编排、字段映射和 SeaTunnel 配置生成；
- 任务发布、提交、停止、执行历史、定时调度；
- 运行日志、读取/写入行数、QPS、数据量、状态和进度指标；
- 告警通道、告警规则及执行记录；
- 数据源插件、DAO 插件、告警插件等扩展机制。

下列合同能力不能仅凭现有 SeaTunnel-Web 判定为已具备，需专项设计或新增实现：

- TDuck 未覆盖或经验证不满足的语义错误识别纠正、任务分配、批量填报编排、合同报告模板与受控分发；
- 文件夹增删改实时同步、DMP/Word/SQL 离线导入；
- 逻辑入湖/数据虚拟化、云边协同与离线缓存；
- 专用/物联网/串口协议解析转换、边缘低功耗接入；
- 链路动态调度、操作回放、根因定位、有效期和暂存周期；
- 合同要求的细粒度权限、持久化审计、行为分析和不可抵赖证据。

### 3.4 OpenMetadata 复用边界

OpenMetadata 可优先映射：元数据采集与版本、数据模型、检索、血缘与影响分析、标签/分类、术语、使用度、数据画像、部分质量测试、资产发现和部分资产概况。

下列能力应作为本项目独立需求进行差距分析和研制：

- 主数据版本、审批和更改告知；
- 领域/对象/主题资源编目及合同特定目录模型；
- 数据标准兼容检查、标准数据元和标准全生命周期审批；
- 外部数据字典集成同步；
- 数据历史版本比较（区别于元数据版本）；
- 质量整改工单与合同格式质量报告；
- 时空数据快速加载、多视角筛选和关联展示；
- 态势模板、价值评估体系、异常行为识别和偏好挖掘。

OpenMetadata 与 SeaTunnel-Web 之间采用 REST API/事件接口和稳定标识映射。SeaTunnel 任务发布、执行和字段映射变化应生成受控的 pipeline、lineage 和 column-lineage 更新；OpenMetadata 的资产、标签和质量变化通过事件接口同步到统一门户。禁止两个系统直接互写对方数据库。

## 4. 生存周期模型与构建版

采用增量式 V 模型：每个构建版都执行需求细化、设计、实现、单元测试、集成测试和产品评价；项目级需求、设计、测试和产品基线通过正式评审控制。

| 构建版 | 目标 | 主要内容 | 预期周次 |
| --- | --- | --- | --- |
| B0 / 技术验证版 | 关闭高风险技术路线 | 国产环境构建、TDuck 版本/许可证/二开与统一身份原型、SeaTunnel 性能基线、OpenMetadata 百万级容量验证、物理/逻辑入湖方案、云边断网续传、统一审计原型 | W1～W10 |
| B1 / 核心骨架版 | 打通两个 CSCI 主链路 | TDuck 表单—采报任务—结果入库链路；数据源—引接任务—执行—监控—入湖链路；元数据—目录—检索—血缘—质量链路；统一门户、权限和审计 | W11～W20 |
| B2 / 功能完整版 | 覆盖全部合同功能 | 采报规则/批量填报/报告、协议/边缘、回放/态势、标准/主数据/字典、时空/价值/行为分析 | W21～W30 |
| B3 / 性能与验收候选版 | 功能冻结并达到测试就绪 | 性能优化、安全加固、国产环境适配、故障恢复、文档与追踪闭环 | W31～W36 |
| V1.0 / 交付基线 | 通过合格性测试和验收 | 合格性测试、第三方测试、配置审计、安装移交和交付 | W37～W48 |

## 5. 分阶段开发计划

### 阶段 0：启动、标准受控与软件策划（W1～W2）

对应 GJB 2786A 软件项目策划和监控、软件开发环境建立，以及 GJB 438C 的 SDP 策划。

主要活动：

- 取得合同、技术协议、GJB 2786A、GJB 438C 及相关标准的受控副本；
- 确认两个 CSCI 的标识、重要性等级/关键性、安全保密等级和交付边界；
- 建立标准条款符合性矩阵、GJB 438C 文档剪裁表和项目术语表；
- 确认组织、独立质量保证、独立测试、配置控制委员会（CCB）和联合评审机制；
- 建立项目开发库、受控库、产品库及权限；冻结工具链、国产化目标环境和离线构建方案；
- 形成规模/工作量初估、48 周进度网络、风险清单和测量计划；
- 对 SeaTunnel-Web、SeaTunnel、OpenMetadata 及全部三方依赖开展来源、许可证、漏洞、版本、哈希、SBOM 和可维护性登记。

阶段输出：SDP V0.1、配置管理分计划、质量保证分计划、风险清单、测量计划、文档剪裁表、复用软件清单、开发环境基线。

出口准则：受控标准齐备；范围、CSCI 和责任边界获批；所有输入材料有唯一版本；未解决的合同歧义已形成正式问题单。

### 阶段 1：系统/软件需求分析与需求基线（W3～W6）

对应系统需求分析、软件需求分析和运行方案分析。

主要活动：

- 将合同 Sheet1、Sheet2、Sheet3 和两个指标 Markdown 合并为唯一需求源；
- 补齐 `ZCGL-GN-03`，澄清 Sheet1 第 239～240 行错标问题；
- 为每条合同要求分配软件需求、接口需求、数据需求、安全需求、性能需求和验证方法；
- 明确云、边、端三种部署方式，云侧容器化和边/端裸部署约束；
- 建立操作场景、异常场景、降级模式、恢复模式和保密约束；
- 建立 SeaTunnel-Web/OpenMetadata 的复用适用性、限制项和替代方案；
- 为每个性能指标形成测试剖面和基准数据集，不把估算值当作测试证据；
- 建立双向需求追踪：合同 → SSS/SRS/IRS → 验证方法。

阶段输出：OCD/运行方案输入、两个分系统 SSS 分卷或章节、两个 SRS、IRS、需求追踪矩阵、复用软件评价报告/记录、性能测试剖面。

里程碑：需求评审（建议 SRR）。

出口准则：合同功能和性能要求分配率 100%；每条需求唯一、可验证、无未批准 TBD；高风险需求有原型或验证计划；需求基线 `BL-REQ` 建立。

### 阶段 2：系统/体系结构与初步设计（W7～W10）

对应系统设计、CSCI 体系结构设计、关键需求处理和计算机资源利用策划。

主要活动：

- 设计统一门户、统一身份、RBAC/数据权限、审计、消息、文件和搜索公共能力；
- 设计 SeaTunnel-Web 企业扩展层，遵循“外部集成 → 独立模块 → SPI → 通用扩展点 → 最小核心补丁”的顺序；
- 设计 OpenMetadata 适配层、实体/标识映射、血缘发布、事件订阅、搜索代理和 SSO；
- 设计云边端拓扑、断网自治、缓存优先级、补传、冲突解决和远程升级；
- 设计物理入湖与逻辑入湖边界，确认数据虚拟化产品或自研范围；
- 设计国产数据库、操作系统、中间件和国密组件适配；
- 完成 B0 技术验证，重点验证 200MB/s 小数据传输目标、百万元数据、6500 质量规则、文件增量、逻辑入湖和断网续传；
- 记录所有关键技术决策及理由，形成 ADR 和复用限制清单。

阶段输出：SSDD、总体架构图、接口清单、部署设计、数据架构、B0 原型及验证报告、资源预算、关键技术 ADR。

里程碑：初步设计评审（建议 PDR）。

出口准则：所有关键需求有架构归属；关键接口有责任方；高风险技术路线已验证或有获批降险措施；体系结构基线 `BL-ARCH` 建立。

### 阶段 3：详细设计、数据库设计与测试策划（W11～W14）

对应软件设计、测试策划、软件产品标准建立。

主要活动：

- 分别编制 `CJYJ-CSCI`、`ZCGL-CSCI` 的 SDD；
- 编制统一身份、OpenMetadata、SeaTunnel、边缘端、外部字典、消息、文件和地图服务的 IDD；
- 编制业务库、审计库、任务扩展库、映射表和索引设计 DBDD；
- 将 SRS 需求分配到软件单元、数据库对象、接口和测试项；
- 编制 STP 和首版 STD，形成单元、单元集成、CSCI 合格性、系统集成和系统合格性测试层次；
- 明确编码标准、静态分析规则、复杂度阈值、单元测试要求、依赖准入规则和安全编码要求；
- 明确性能测试计时边界、数据预置、监控采样、重复次数和统计判定。

阶段输出：两个 SDD、IDD、DBDD、STP、STD V0.1、接口模拟器、测试数据规范、代码与数据库规范。

里程碑：详细设计评审（建议 CDR）。

出口准则：需求到设计分配率 100%；接口、数据模型和错误码冻结；测试可追踪率 100%；详细设计基线 `BL-DES` 建立。

### 阶段 4：软件实现与单元测试（W15～W26）

对应软件实现和单元测试。两个 CSCI 并行开发，每个迭代 2 周，每次迭代形成可构建、可测试、可追踪的软件增量。

数据采集引接软件工作包：

- `CJYJ-WP1`：SeaTunnel-Web 基线固化、企业模块/SPI、统一身份权限和持久化审计；
- `CJYJ-WP2`：全量/增量/CDC、文件夹增量、离线文件导入、数据探查和多表批量作业；
- `CJYJ-WP3`：任务配置、实时/周期调度、告警、日志、报表、数据湖资源和物理/逻辑入湖；
- `CJYJ-WP4`：传输加密、身份鉴权、云边同步、离线缓存、协议解析转换和低功耗边缘接入；
- `CJYJ-WP5`：采集态势、链路配置/调度、操作回放、故障定位、拓扑发布和有效期管理。

数据资产管理软件工作包：

- `ZCGL-WP1`：OpenMetadata 受控部署、适配器、元数据采集/模型/版本/血缘/影响分析；
- `ZCGL-WP2`：主数据、领域/对象/主题资源编目、标签分类分级、术语和推荐；
- `ZCGL-WP3`：数据标准、标准数据元、兼容检查、审批发布、外部数据字典同步；
- `ZCGL-WP4`：数据维护版本、质量规则/监控/整改/报告、全域检索和资产一张图；
- `ZCGL-WP5`：时空快视、态势定制、价值评估、用户行为分析和异常识别。

每个工作包的完成定义：

- 代码和数据库变更关联需求/设计标识；
- 至少一名非作者完成代码评审，安全关键变更至少两名审批；
- 单元测试、静态分析、依赖/许可证/漏洞扫描通过；
- API、配置、迁移、部署和回滚说明同步更新；
- 不修改已发布迁移；上游核心补丁登记来源、原因、删除条件和回归测试；
- 形成单元测试记录、产品评价记录和问题/更改报告。

### 阶段 5：单元集成、CSCI 集成与功能冻结（W27～W32）

对应单元集成和测试，以及 CSCI 内部集成。

主要活动：

- 完成 SeaTunnel Engine、数据库、消息、边缘端、OpenMetadata、搜索引擎、对象存储和地图组件集成；

- 验证统一身份、最小权限、数据源密钥保护、审计完整性和敏感信息脱敏；
- 完成上一版本数据库升级、历史任务兼容和 OpenMetadata/SeaTunnel 版本兼容测试；
- 对所有缺陷进行分类、根因分析、影响分析、纠正和回归；
- 功能冻结后只允许经 CCB 批准的缺陷修复进入候选版。

阶段输出：集成测试记录、缺陷和回归记录、兼容矩阵、升级/回滚演练记录、候选版本 B3。

出口准则：合同功能覆盖率 100%；阻断/严重缺陷为 0；需求—测试双向追踪完整；测试基线 `BL-TEST` 建立。

### 阶段 6：CSCI 合格性测试与配置审计（W33～W39）

- 评审稿、批准稿、修改稿和交付稿使用不同状态；批准稿转入受控库，交付稿转入产品库。
- 图、表、测试记录、需求数据库和工具导出物如作为文档组成部分，必须具有版本、生成规则、来源和可重复导出方法。

## 8. 全过程管理要求

### 8.1 需求与证据追踪

统一追踪链如下：

`合同条款/指标 → 系统或分系统需求 → SRS/IRS → SDD/DBDD/IDD → 软件单元/代码提交/数据库迁移 → STD 测试用例 → STR 结果 → 问题/更改报告 → SPS/SVD/交付物`

标识建议：

- 功能需求：`CJYJ-SRS-F-###`、`ZCGL-SRS-F-###`；
- 性能需求：`CJYJ-SRS-P-###`、`ZCGL-SRS-P-###`；
- 接口需求：`IRS-<接口域>-###`；
- 设计单元：`CJYJ-SDD-U-###`、`ZCGL-SDD-U-###`；
- 测试用例：`CJYJ-STD-<层级>-###`、`ZCGL-STD-<层级>-###`。

每次正式评审前执行正向和反向追踪检查，不允许出现无来源需求、无设计需求、无测试需求、无需求代码或无结论测试。

### 8.2 配置管理与基线

| 基线 | 内容 | 建立时点 |
| --- | --- | --- |
| `BL-CONTRACT` | 合同、技术协议、指标表、批准澄清单 | 启动阶段 |
| `BL-REQ` | SSS/SRS/IRS、需求追踪矩阵 | SRR 后 |
| `BL-ARCH` | SSDD、架构与部署、ADR | PDR 后 |
| `BL-DES` | SDD/IDD/DBDD、STP/STD 初版 | CDR 后 |
| `BL-TEST` | 功能冻结软件、正式 STD、测试环境/数据 | TRR 后 |
| `BL-PROD` | 源码、构建、迁移、镜像/安装包、SBOM、SPS/SVD/STR | 合格性测试后 |
| `BL-DELIVERY` | 需方批准的全部交付项 | 验收移交后 |

所有基线变更必须提交问题报告/更改报告，完成原因、影响范围、追踪影响、测试影响、进度/成本/风险和回退分析，经 CCB 批准后实施。禁止用口头通知、直接改文档或强推 Git 历史替代变更控制。

### 8.3 复用软件和开源治理

- 固定 SeaTunnel-Web 上游提交、SeaTunnel 版本、OpenMetadata 版本及全部依赖，不使用 `latest`、浮动版本或不可复现安装；
- 保留 LICENSE、NOTICE、第三方许可证、源码来源、补丁、构建脚本和校验和；
- 每个企业核心补丁登记原因、影响、上游替代状态、删除条件和回归测试；
- 上游同步作为正式软件升级，经影响分析、数据库升级测试、回归、SBOM/漏洞扫描和 CCB 审批；
- 生产软件在隔离环境可离线、可重复构建，产品库保存源代码、依赖包、工具版本、镜像 digest 和构建日志；
- OpenMetadata、SeaTunnel 及连接器的许可证和漏洞结论由质量/安全人员复核，未经批准不得进入产品基线。

### 8.4 质量保证、产品评价和独立性

- 质量保证人员独立检查过程遵循、工作产品、评审、测试、配置和问题关闭情况；
- 测试负责人不由相应功能的主要开发人员兼任，合格性测试结果不可由开发人员直接改写；
- 每阶段形成产品评价记录，问题必须有责任人、严重度、截止时间、纠正措施和验证结论；
- 联合技术评审和联合管理评审均记录议题、材料版本、结论、遗留项、责任人和关闭证据；
- 里程碑通过条件不是“文档已提交”，而是材料已基线、问题已关闭或经批准延期、追踪和证据完整。

### 8.5 保密与安全

- 根据项目密级设置开发区、测试区、受控库和产品库访问权限，文档、代码、日志、测试数据和介质均按标识管理；
- 数据源凭据、证书、令牌和密钥不得明文入库、入日志或进入前端响应；
- 建立角色、组织、项目、数据源、任务、资产、字段/标签等细粒度授权，前端隐藏不替代后端鉴权；
- 审计记录至少包含主体、时间、来源、对象、操作、结果、前后值摘要、关联追踪号和完整性保护；
- 对上传、协议解析、表达式/SQL、外部命令、插件、反序列化和文件预览开展专项安全评审与测试；
- 如合同要求国密或特定安全标准，算法、设备、证书和测试机构必须由需方确认，不在需求未确认时自行替代。

| 详细设计评审（CDR） | 软件单元、数据、接口、测试可实现性 | `BL-DES` |
| 测试就绪评审（TRR） | 软件冻结、环境、数据、STD、追踪 | `BL-TEST` |
| 合格性测试评审 | STR、缺陷、性能、安全和回归 | `BL-PROD-RC` |
| 配置审计/交付评审 | 功能/物理一致性、SPS/SVD、可复现性 | `BL-PROD` |
| 验收/移交评审 | 合同符合性、现场结果和交付完整性 | `BL-DELIVERY` |

评审名称和是否作为合同正式评审点，应由总体单位/需方确认；无论名称如何，评审输入、版本、结论、遗留项和关闭证据必须受控。

### 10.2 核心测量项

- 合同需求分配率、需求追踪覆盖率、需求变更率；
- 设计/代码/测试评审问题密度和按期关闭率；
- 单元测试通过率、关键模块覆盖率、静态分析严重问题数；
- 缺陷发现/关闭趋势、缺陷重开率、阶段逃逸率；
- 构建成功率、可重复构建率、依赖漏洞和许可证问题数；
- 性能指标裕量、资源利用率、72 小时/约定时长稳定性结果；
- 文档计划完成率、文档审查问题数、基线一致性问题数；
- 风险暴露趋势、纠正措施关闭率、上游补丁数量和同步成本。

所有门禁至少要求：追踪覆盖率 100%，阻断/严重问题为 0，未关闭一般问题有批准的计划，正式测试和交付物可由受控基线复现。

| 风险 | 等级 | 前置措施 |
